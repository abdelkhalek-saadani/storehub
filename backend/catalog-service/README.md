# catalog-service

The code follows a feature-package structure, where top-level packages represent features, and nested directories
represent the technical split (services, entities, etc.).

## Quick Start

To run using docker:

```shell
docker build -t catalog-image .
docker run -e SPRING_PROFILES_ACTIVE=e2e --env-file .env --network host --name catalog-app catalog-image
```

Assuming rabbitmq broker is running on `5672,15672` and postgres database is running on `5432` and keycloak on
`http://auth-server:8088`

## Authentication & Authorization

Auth is JWT-based. Store owner endpoints are protected with the `STORE_OWNER` role, while inter-service endpoints
(e.g. reservation endpoints and the price calculation endpoint) are protected with the `SERVICE` role.

## Events Consumed

- **Store Created** — updates its shadow store table (a mirror of order-service's store table).
- **User Created** — updates its shadow user table.
- **Items Released** — releases retained items.
- **Slot Released** — releases a retained slot.
- **Order Created** — links the now-persisted order ID to the item and slot reservation records (created before
  the order itself was persisted, so they initially have no order ID).

## Inventory

Role: performs reservation/release of order items, and exposes an endpoint for items availability checks.

### Stock Modeling

Product quantity is modeled with two objects: `Stock` and `StockMovement`.

- **Stock** — mutable, linked to a product, and holds its quantity state. It owns the logic to update the product's
  on-hand, available, and reserved quantities: `quantityAvailable = quantityOnHand - quantityReserved`.
- **StockMovement** — an append-only ledger that serves as the history of stock changes.

Reservations are held as a mutable `Reservation` object, linked to a product, holding the reserved quantity and a
state: `ACTIVE -> {CONFIRMED | RELEASED | EXPIRED}`. The state is set to `CONFIRMED` when order is shipped.

### Reservation & Release Logic

This logic lives in `StockService`.

`reserveForOrder` calls `reserveForOrderTx` to perform the reservation for an order. `reserveForOrderTx` is
transactional, so if a reservation fails for one item, the reservation for all items in the order is rolled back.

One subtlety: `@Transactional` only takes effect when a method is called through the Spring-managed proxy (i.e. via
dependency injection). Calling `reserveForOrderTx` directly from within its own class would bypass the proxy and
call it as a plain method, silently losing transactional behavior. To avoid this, `StockService` injects itself
(a self-reference), so that calling `reserveForOrderTx` goes through the proxy and transactional behavior takes
effect as expected.

### Concurrency Strategy

Stock updates use optimistic locking via a `version` column, since race conditions are treated as the exception
rather than the norm here. On race conditions the stock service retries for `MAX_RETRIES=3` before throwing.
A repository method using pessimistic writes is also kept in place, ready to switch to
for hot SKUs (e.g. during a sale event).

## Pricing

Role: applies discounts to a list of items (a cart or order) and calculates line-item totals and the overall total.

Discount types are implemented using the **Strategy** pattern: a `DiscountStrategy` interface defines an `apply`
method, and each discount type implements it with its own business logic and attributes (e.g. a quantity discount
has a `minimumQuantity` field, while a "Buy X Get Y" discount has `requiredQuantity` and `freeQuantity`). A
**Factory** pattern is used to create the appropriate discount strategy from a unified holder object.
`@JsonTypeInfo`/`@JsonSubTypes` (Jackson polymorphic typing) is used for serialization/deserialization.

## Products

Role: manages products, discounts, and sale events.

JPA Specifications are used to apply filtering rules, along with pagination.

## Slot

Role: performs slot reservation/release for orders, and exposes an endpoint for slot availability checks.

### Slot Generation

Delivery slots are generated from a slot config. A **delivery slot** has a start time, a duration, and a capacity.
A **slot config** is the template used to generate concrete slots: it defines a start time, an end time, a duration
(concrete slots are generated by stepping from the start time to the end time in increments of the duration), a
capacity, and a specific day of the week (e.g. Monday, Sunday).

Slot generation runs:

- On every slot config creation or update: syncing any already-generated future slots, while excluding slots that
  have already been reserved or manually edited.
- Every midnight, for a 7-day window: looking at existing configs and generating their concrete slots 7 days ahead.

### Reservation & Slot States

For each order, a reservation record is created and has one of these states: `RESERVED`, `CONFIRMED`, `RELEASED`,
`EXPIRED`.
State goes to `CONFIRMED` when order is shipped.

Each concrete slot can go through these states: `OPEN`, `FULL`, `CLOSED`, `CANCELLED`.

## Store

This package mirrors store state from order-service. It's used by other packages to associate an authenticated
user (owner) with their store. It holds a minimal representation of the store: store ID, owner ID, and store slug.

The shadow table is kept in sync with order-service in two ways:

- Events received from order-service on every store creation.
- A nightly reconciliation job, where catalog-service calls an order-service API to fetch a batch of existing
  stores and updates the shadow table with anything missing.

When catalog-service calls order-service, a `RestClient` is used, configured with an interceptor that attaches a
JWT fetched from Keycloak using the `order-internal-service` client (see [auth-server docs](../../keycloak/README.md)).

## User

This package mirrors user state from order-service. It's used by other packages to associate an incoming Keycloak
ID (from the JWT claim) with the internal user ID, which in turn can be associated with that user's store via the
store shadow table. It holds two fields: Keycloak ID and user ID.

The shadow table is kept in sync with order-service via events received on every user creation. A reconciliation
job, similar to the store shadow's, is planned for the future.
